"""A SECOND, deliberately different, hypothetical project's `pygetm_config.providers`
registry (FURTHER item 7: "How will the Data provenance work for a different
project?... depending on the e.g. meteo source the paths and names will be
different"). Not OceanICU -- a made-up coastal setup ("CoastalApp") using
different upstream data sources entirely, to prove the extension point in
providers.py carries no OceanICU assumptions: nothing in `make_provider_slot`/
`discover_provider_sections` cares what a project calls its providers or what
extra params they need.

Contrast with OceanICU's real registry
(`OceanICU/oceanicu_3d/driver/oceanicu_providers.py`, a separate repo --
not shipped here, since it's genuinely project-specific rather than the kind of
generic material this repo's own examples/ should hold):
- meteo: GFS (global, 0.25deg forecast/analysis grib->nc, cycle-based) instead of
  ERA5 (reanalysis) -- different extra params (`cycle_hour`, `forecast_hours`)
  because the underlying data has a genuinely different shape (GFS is issued in
  discrete forecast cycles; ERA5 is a continuous hourly reanalysis archive).
- boundaries: HYCOM (a single global ocean reanalysis covering both barotropic
  and baroclinic fields) instead of OceanICU's split TPXO-for-tides/
  CMEMS-for-everything-else -- so this project needs only ONE boundaries role,
  not two.
- No river_discharge role at all -- this hypothetical setup has no open rivers.

This module's `meteo` role deliberately reuses the SAME role name as
OceanICU's real registry's `meteo` role -- realistically, two unrelated
projects' "where does weather forcing come from" role would often get the same
obvious name. In practice you install exactly one project's provider package
into the environment you build that project's schema in (see providers.py's
"consuming project" framing -- this was never meant to support multiple
unrelated projects' registries live in one environment at once). If you DID
try to install both, `discover_provider_sections()`'s existing
conflict-detection (see `tests/test_providers_extension_point.py::
test_discover_provider_sections_conflict_raises`) catches a `meteo` collision
loudly rather than silently letting one project's registry shadow the other's
-- proven concretely (this registry plus a second synthetic one) in
`tests/test_provider_registry_example.py::
test_two_projects_with_same_role_name_collide_loudly`. This registry works
correctly on its own in a single-project build_schema() call, per
`test_build_schema_discovers_coastalapp_providers`.
"""

from __future__ import annotations

from pygetm_config.model import ChoiceSpec, Importance, ParameterSpec, TypeRef
from pygetm_config.providers import make_provider_slot


def register_coastalapp_providers() -> dict[str, ChoiceSpec]:
    meteo = make_provider_slot(
        "meteo",
        {
            "GFS": (
                ParameterSpec(
                    name="cycle_hour",
                    type=TypeRef(kind="scalar", scalar_type="int"),
                    default=0,
                    help="forecast cycle to use (0/6/12/18 UTC)",
                    importance=Importance.BASIC,
                ),
                ParameterSpec(
                    name="forecast_hours",
                    type=TypeRef(kind="scalar", scalar_type="int"),
                    default=384,
                    help="how many forecast hours to pull per cycle",
                    importance=Importance.ADVANCED,
                ),
            ),
        },
        default="GFS",
    )

    boundaries = make_provider_slot(
        "boundaries",
        {
            "HYCOM": (
                ParameterSpec(
                    name="experiment",
                    type=TypeRef(kind="scalar", scalar_type="str"),
                    help="HYCOM experiment/run identifier, e.g. 'GLBy0.08/expt_93.0'",
                    importance=Importance.BASIC,
                ),
            ),
        },
        default="HYCOM",
    )

    return {"meteo": meteo, "boundaries": boundaries}
