What belongs in YAML vs. what belongs in a project driver script

pyGETM configuration is genuinely two-folded, and pretending otherwise would be dishonest about how real setups work. pygetm-config covers one half well; the other half is, and should stay, Python. This doc states the dividing line precisely, using OceanICU's real run_model.py/cfg_*.py as the concrete reference (verified directly against that source, not from memory) since it's the best available example of a real, working setup that mixes both.

The principle

YAML (validated by pygetm_config's schema): any value that plugs directly into a typed pyGETM API parameter, once you already know what that value is. Grid size, physics/numerics constants, which strategy object to use and its parameters, open-boundary/river positions, output file/variable selections, run timing. This is "what should the model do," expressed as data. It's exactly what PygetmConfigSchema models, and it's genuinely setup-independent in shape — only the values differ between setups (confirmed directly: all five of OceanICU's *_model_config.yaml files are structurally byte-identical, only leaf values differ).

A project driver script (a run_model.py, one per project — possibly one per group of setups): anything that requires interpreting an external, non-pyGETM-native data source or convention, or that is genuinely dynamic/ data-dependent rather than a fixed choice from a menu. This is "how do I obtain the raw ingredients," expressed as code. Two concrete categories:

  1. Reading a specific file with a specific, non-generic convention — the general case of this stays Python (see below for one specific case that turned out not to). OceanICU's _create_domain_nse (run_model.py) reads bathymetry via: python with netCDF4.Dataset(cfg.domain.path) as nc: nc.set_auto_mask(False) domain = pygetm.domain.create_spherical( lon=nc["lon"][:], lat=nc["lat"][:], H=nc["depth_rx0_0p20"][...], mask=nc["ocean_mask"][...], z0=0.01, ) _create_domain_amm7 reads the same conceptual thing — a bathymetry file — with different variable names: bathymetry instead of depth_rx0_0p20, mask inferred from np.ma.masked_equal(H, -10.0) instead of a separate ocean_mask variable, plus a follow-up domain.mask_indices(1, 2, 353, 354) call. The variable-naming and mask-convention difference between these two turned out to be fully generalizable — it's just which variables to read and how to derive water/land, not a difference in behavior — so pygetm-config now ships a BathymetryFile choice under domain: (schema. _build_bathymetry_file_choice, loader.build_domain_from_bathymetry_file) with path/depth_variable/ lon_variable+lat_variable (or x_variable+y_variable)/mask_variable/ mask_fill_value/z0 fields that expresses both conventions as data, verified against both real files (synthetic nse-style and amm7-style NetCDFs in tests/test_loader.py). _create_domain_amm7's trailing domain.mask_indices(1, 2, 353, 354) call is a genuinely different kind of thing — an ad hoc, setup-specific manual mask correction, not part of "reading the file" — and is NOT covered by BathymetryFile; a setup needing that still writes its own driver code calling loader.build_domain_from_bathymetry_file (or build_domain) and then patching the result, same as any other case where domain is built outside the loader. pygetm-config's DataSourceSpec.role="domain_grid_field" remains schema-only intent (see model.py's docstring) for the genuinely bespoke cases this doesn't cover — it was never meant to replace bespoke driver code entirely, just this one common, generalizable sub-case of it.

  2. Genuinely dynamic, data-dependent content. OceanICU's rivers are not a static list anywhere. cfg_rivers.py opens an EMORID/JRC NetCDF, computes valid_river = ds[Qmean_name] > threshold, filters further by domain.contains(lon, lat), and calls add_by_location once per surviving index — the set of rivers depends on the threshold and the domain's exact footprint. Freezing this into a static YAML list would silently lose the dynamic filtering (a bathymetry/domain change would need someone to remember to regenerate the list by hand). This has to stay a loop in Python.

A third category: data provenance, which is neither of the above

OceanICU's hydrography/boundaries.{barotropic,baroclinic}/meteo/rivers sections describe where forcing data comes from — source: CMEMS|WOA|TPXO|..., each with its own folder/folder_template/filename_template ({setup}/{model}/{scenario}/{start_date}/{end_date} placeholders, confirmed via cfg_utils.py's resolve_folder/resolve_path) and often a date range. This is genuinely data, not code — but it's not a pyGETM concept either (pyGETM only ever sees a final resolved file path). pygetm_config.providers exists for exactly this: a generic source:-discriminated building block with zero concrete provider names shipped, because CMEMS/WOA/TPXO/ERA5/EMORID are OceanICU-specific, not general pyGETM concepts. OceanICU/oceanicu_3d/driver/oceanicu_providers.py (a separate repo) is a real, populated OceanICU registry (CMEMS/WOA/TPXO/ERA5/CMIP6/emorid as real ChoiceSpec entries), plus this repo's own examples/generic_project_providers.py, a second, different hypothetical project's registry proving the mechanism is genuinely project-agnostic — see docs/providers.md for the full writeup. Not installed as a real entry point — oceanicu_3d still has no pyproject.toml to hang one off — but actively registered anyway via the zero-packaging PYGETM_CONFIG_PROVIDERS env var, which oceanicu_driver.py's own main() sets automatically before calling build_schema(). This means nse_from_oceanicu.yaml's hydrography:/ boundaries.*:/river_discharge:/meteo: sections ARE genuinely schema-validated today (a deliberately-invalid hydrography.source value is caught with a real ValidationError, not silently ignored) — every real domain config validates cleanly against this registry with zero manual export needed, since oceanicu_driver.py sets the env var itself. Turning a chosen provider entry into an actual pygetm.input.from_nc(...) call doesn't need new machinery, though -- the existing data_assignments: section (kind: file + pre_transform_scale/ pre_transform_offset) already does exactly that generically, verified against real ERA5 files for nse_from_oceanicu.yaml's meteo forcing (simulation.airsea.t2m/d2m/u10/v10/sp/tcc, with -273.15 offsets converting ERA5's Kelvin to pyGETM's expected °C) -- see that file's data_assignments: block and comments. What's still future work is only automating that: deriving those six entries from providers.meteo's abstract source: ERA5, folder: ... instead of writing them by hand once per setup, which really is provider-specific (ERA5's real file-naming convention, which fields need which unit conversion) and not a generic pygetm-config capability.

What this means in practice for "do we need a different run_model.py per setup?"

Yes, in general — but the pyGETM-schema-covered part of the driver doesn't need to differ, because loader.py's functions each take an already-built domain/sim as an argument rather than constructing it internally:

build_domain(config, schema)                    # generic path, OR build your own:
add_open_boundaries(domain, config, schema)      # domain from ANY source
add_rivers(domain, config, schema)               # (built by loader, or by hand)
build_simulation(domain, config, schema)
apply_data_assignments(sim, domain, config, schema)
configure_output(sim, config, schema)
start_simulation(sim, config, schema)
run_loop(sim, config, stop)

For OceanICU's nse/amm7-style setups specifically, even the first line stays generic now — build_domain(config, schema) reads domain:'s own BathymetryFile choice and handles both conventions, so oceanicu_driver.py (in OceanICU/oceanicu_3d/driver/ -- see below) no longer has its own domain-building code at all. A project driver only needs to replace the first line — build domain however the project needs — for the genuinely bespoke residual: a manual mask correction like _create_domain_amm7's domain.mask_indices(...) call, or a data source that isn't "a NetCDF file with named variables" at all. Only that residual and the river-loading loop need to differ per project in the general case; the boundary positions, physics parameters, and output configuration move fully into YAML and stop needing Python at all — a genuine improvement over hardcoding them per-setup in cfg_boundaries.py as OceanICU does today (see the worked conversion below).

Worked example: converting nse_model_config.yaml

The full converted file and its accompanying driver live in the OceanICU repo, not here (they're genuinely OceanICU-specific, unlike the project-agnostic material this repo ships) — see OceanICU/oceanicu_3d/NSe/config/nse_from_oceanicu.yaml and OceanICU/oceanicu_3d/driver/oceanicu_driver.py (needed only for rivers -- domain-building is fully generic, see above), plus that directory's README.md. Summary of what moved where:

OceanICU today Where it lives now
momentum.{An,Am,cnpar}, vertical_coordinates, internal_pressure, simulation.{runtype,Dcrit,Dmin}, runtime.{timestep,split_factor}, switches.* YAML, pygetm-config-validated, direct value mapping
momentum.avmol YAML, but note: pyGETM's actual parameter is avmmol (Momentum.__init__, verified) — OceanICU's config uses a name that no longer matches pyGETM's own API. Concrete evidence pyGETM's API moves faster than downstream configs.
simulation.calendar Nowhere in the new schema — Simulation.__init__ has no calendar parameter; this was presumably consumed elsewhere in OceanICU's own date-handling, not passed to pyGETM directly. Flagged as unmapped rather than silently dropped.
Open boundary positions (cfg_boundaries.py's 9 hardcoded add_by_index calls for "nse") YAML, open_boundaries: collection — a genuine improvement: this was Python-only before (setup name → if branch → hardcoded indices), now it's data like everything else in that section.
output.{meteo,tides,barotropic,baroclinic} booleans + separate output.yaml variable-list file YAML, output.files: — collapsed into explicit file entries with their variable lists inlined (see the worked file), since pygetm-config's output.files collection doesn't have oceanicu's separate boolean-flag/variable-list-file split.
Bathymetry reading (_create_domain_nse, NetCDF variable names, mask convention) YAML, domain:'s BathymetryFile choice — turned out to be fully generic (see above); oceanicu_driver.py no longer builds the domain itself
Rivers (EMORID read + threshold filter) Stays Python — oceanicu_driver.py's own driver/scripts/rivers.py
hydrography/boundaries.*.{source,...}/meteo/river_discharge.*.{source,...} data-provenance sections YAML, schema-validated — real oceanicu_providers.py registry, registered via PYGETM_CONFIG_PROVIDERS (oceanicu_driver.py sets it automatically); actually wiring a chosen provider's data into data_assignments: is still hand-written per setup (see above), just the provider choice itself is validated now
