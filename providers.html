Populating a pygetm_config.providers registry

src/pygetm_config/providers.py ships the generic shape of a data-provenance choice (a source:-discriminated ChoiceSpec, plus a shared folder/ folder_template/filename_template/start_date/end_date base every provider gets for free) with zero concrete provider names -- deliberately, and enforced by a test (test_no_concrete_provider_names_shipped), since pygetm-config must stay independent of any one project (see docs/yaml_vs_python.md's "third category" section for why provider choice is data, not a pyGETM concept, and therefore doesn't belong in the core schema). This doc answers the two questions that were still open once that shape existed but nobody had actually used it: "how does a populated registry work, concretely, for OceanICU?" and "how would this look for a completely different project?"

How discovery actually works

schema.build_schema() calls providers.discover_provider_sections(), which looks in TWO places for a project's registered provider sections, and merges whatever it finds from either (or both) into the schema's own sections, as ordinary Sections -- from that point on they're indistinguishable from a core section: they show up in pygetm-config dump/template/validate/edit like anything else, get YAML-rendered under their (possibly dotted) key, and participate in normal validation.

  1. The pygetm_config.providers entry-point group (Python's standard importlib.metadata.entry_points mechanism) -- needs the registering project to be pip-installed (editable or otherwise) with a [project.entry-points."pygetm_config.providers"] table in its pyproject.toml. The "proper" path once a project has real packaging.
  2. The PYGETM_CONFIG_PROVIDERS environment variable -- a comma-separated list of path/to/file.py:function_name (loaded directly off disk, via importlib.util.spec_from_file_location -- no install, no pyproject.toml, nothing needs to be on sys.path) or importable.module:function_name (needs the module importable, e.g. via PYTHONPATH, but still no pip install) entries. This is the answer to "how do I use a provider registry without turning my project into an installable package": you don't need to -- point this env var straight at the .py file: bash export PYGETM_CONFIG_PROVIDERS=/path/to/OceanICU/oceanicu_3d/driver/oceanicu_providers.py:register_oceanicu_providers pygetm-config validate some_config.yaml # now sees hydrography/boundaries.*/meteo/river_discharge Verified working end to end against the real file, not just described here. OceanICU's own driver/oceanicu_driver.py sets this env var automatically (via os.environ.setdefault, pointing at its own oceanicu_providers.py), so this manual export is only needed when invoking pygetm-config directly against an OceanICU config, bypassing the driver.

Each source must resolve to a zero-argument callable returning dict[str, ChoiceSpec] (role name -> provider slot, built via providers.make_provider_slot).

If neither source has anything registered -- the default for pygetm-config's own dev environment, which intentionally has no project-specific package installed and no env var set -- discover_provider_sections() returns {} and build_schema() behaves exactly as if the mechanism didn't exist. Nothing about the core schema depends on any provider registry being present.

Collision safety: build_schema() checks every discovered provider role against the core section keys (domain, open_boundaries, rivers, output, ...) and raises ValueError if one collides, rather than silently letting a provider role shadow a core section (or vice versa -- section lookup by key is a first-match search, so a silent collision would just make one of the two unreachable). providers.discover_provider_sections() separately raises if two different sources -- entry points, env-var entries, or a mix of both -- register the same role name, for the same reason. Both are exercised by real tests, not just described here (see tests/test_providers_extension_point.py for the env-var mechanism itself and tests/test_provider_registry_example.py for a full worked registry).

Worked example: OceanICU

A full, real registry using OceanICU's actual provider vocabulary lives in the OceanICU repo itself, not here: OceanICU/oceanicu_3d/driver/oceanicu_providers.py -- genuinely OceanICU-specific, so it lives with the project it describes; pygetm-config ships zero concrete provider names or project-specific example configs of its own (see the summary table below, and that directory's own README.md). It registers: hydrography (CMEMS/WOA), boundaries.barotropic (TPXO, with a tpxo_folder extra param), boundaries.baroclinic (CMEMS), meteo (ERA5, with evaporation/shortwave_method/longwave_method extras), and river_discharge (emorid, with file/threshold extras -- named river_discharge, not rivers, because the core schema already has a rivers section for open-boundary river positions; an earlier draft of this example used rivers and build_schema()'s own collision check caught it immediately, which is exactly the safety net it's there for).

This file is not installed by pygetm-config itself, and doesn't need to be installed anywhere to work: oceanicu_3d is a script directory, not a packaged project, so it uses the PYGETM_CONFIG_PROVIDERS env var path (see above), not entry points. driver/oceanicu_driver.py sets that env var itself, automatically, before calling build_schema():

export PYGETM_CONFIG_PROVIDERS=/path/to/OceanICU/oceanicu_3d/driver/oceanicu_providers.py:register_oceanicu_providers

If oceanicu_3d ever gains real packaging, the entry-point path becomes available too (no change needed in oceanicu_providers.py itself):

[project.entry-points."pygetm_config.providers"]
oceanicu = "pygetm_config.oceanicu_providers:register_oceanicu_providers"

Either way build_schema() picks it up with no code change in pygetm-config. This repo's own tests/test_providers_extension_point.py proves the env-var mechanism end to end (using a small registry written to a temp file inside the test, not reaching across repos into OceanICU's, since pygetm-config's test suite must run standalone without the OceanICU repo present) -- the same mechanism is what OceanICU's own driver relies on for real, surfacing hydrography/boundaries.barotropic/boundaries.baroclinic/ meteo/river_discharge in every build_schema() call it makes.

What a validated config against the OceanICU registry looks like -- note meteo: keeps BOTH ERA5: and CMIP6: present at once, only source: picking which is active. This isn't provider-specific: EVERY ChoiceSpec in the schema now works this way (see docs/overview.md) -- providers are just the case that originally motivated it.

hydrography:
  source: CMEMS
  CMEMS:
    folder: /data/boundaries/init_data/nse/
  WOA:
    folder: /data/WOA
boundaries:
  barotropic:
    source: TPXO
    TPXO:
      tpxo_folder: /data/TPXO9
    CMEMS:
      folder: /data/CMEMS_barotropic
meteo:
  source: ERA5
  ERA5:
    folder: /data/ERA5
    evaporation: true
    shortwave_method: 1
    longwave_method: 1
  CMIP6:
    folder: /data/CMIP6
    evaporation: true
    shortwave_method: 1
    longwave_method: 1
river_discharge:
  source: emorid
  emorid:
    folder: /data/EMORID
    file: EMORID_1990_2024.nc
    threshold: 0

This is exactly the shape NSe/config/nse_from_oceanicu.yaml (OceanICU's own real, schema-validated config) uses today -- hydrography, boundaries.barotropic/boundaries.baroclinic, meteo, and river_discharge are all validated against this registry, via PYGETM_CONFIG_PROVIDERS (set automatically by oceanicu_driver.py, see above).

Switching data source per run-folder, nothing else edited

Every ChoiceSpec in the schema (not just providers -- vertical_coordinates, radiation, domain, the output.files per-file type choice, everything) keeps EVERY alternative's fields present at once, each under its own <label>: sub-key, rather than only the chosen one at the top level. Real, raised need: different run-folders should be able to share one base config and switch data source (source: ERA5 vs source: CMIP6) per folder, purely by changing that one field, not by deleting/retyping a whole config block each time -- see docs/overview.md for why this became the universal convention rather than a providers-only special case. pygetm-config template emits EVERY alternative's fields already populated, and pygetm-config validate/yaml_parse.validate_config reads whichever sub-key matches the active source:, validates only that one, and preserves every other sub-key's block verbatim (unvalidated) in the output -- so flipping source: back later doesn't lose the other values either. Falls back to the old flat shape for backward compatibility if the active choice's own sub-key isn't present (e.g. a config written before this convention existed).

A different project

examples/generic_project_providers.py (in this repo) is a second, unrelated, hypothetical project ("CoastalApp") registering its own provider vocabulary: meteo sourced from GFS (a forecast-cycle product, with cycle_hour/forecast_hours extras -- genuinely different shape from ERA5's continuous reanalysis archive, not just a different provider name for the same shape) and a single combined boundaries role sourced from HYCOM (one reanalysis product covering both barotropic and baroclinic fields, unlike OceanICU's split TPXO-for-tides/CMEMS-for-everything-else). Neither this project's registry nor OceanICU's imports or references the other -- providers.py's contract (make_provider_slot/discover_provider_sections) carries no assumptions about either. This is the one project-specific-looking example pygetm-config does ship, precisely because it's explicitly hypothetical rather than describing any real project -- consistent with the package shipping zero real provider names.

tests/test_provider_registry_example.py:: test_build_schema_discovers_coastalapp_providers proves this registry works on its own in build_schema().

One honest wrinkle worth stating explicitly: this example and OceanICU's real one both register a meteo role, since "where does weather forcing come from" is an obvious name any project would reach for independently. In practice you install exactly one project's provider package into the environment you build that project's schema in -- pygetm_config.providers was never meant to merge two unrelated projects' registries into one live schema at once, only to let a single project plug its own vocabulary into pygetm-config's generic mechanism. If two happened to be installed simultaneously anyway, discover_provider_sections()'s existing conflict check catches the role-name collision loudly (raises ValueError) rather than silently letting one project's definition shadow the other's -- test_two_projects_with_same_role_name_collide_loudly proves this concretely (using the CoastalApp example plus a second synthetic registry defined inline in the test), not just the fully-synthetic case in test_providers_extension_point.py.

Summary

Question Answer
Does pygetm-config ship any real provider names? No -- providers.py is shape-only, enforced by a test. examples/generic_project_providers.py is explicitly hypothetical, not a real project.
How does a project add its own? Register a zero-arg callable returning dict[str, ChoiceSpec] under the pygetm_config.providers entry-point group in the project's own package.
What does build_schema() do with it? Merges the returned sections in automatically; raises loudly on a role name colliding with a core section key.
What if two unrelated projects are both installed? discover_provider_sections() raises loudly on a role name collision between them, rather than silently picking one.
Can a config keep multiple sources' data and just switch source:? Yes -- this is how every ChoiceSpec in the schema works now, not just providers: every alternative's fields stay present (each under its own <label>: sub-key) rather than only the active one; real motivating need is different run-folders sharing one base config while pointing at different data sources. See docs/overview.md.
Where's a real, working example? OceanICU/oceanicu_3d/driver/oceanicu_providers.py (a separate repo -- OceanICU's actual vocabulary) and, in this repo, examples/generic_project_providers.py (a different, hypothetical project's, exercised by tests/test_provider_registry_example.py).
Has OceanICU actually adopted this yet? Yes -- driver/oceanicu_driver.py registers oceanicu_providers.py via PYGETM_CONFIG_PROVIDERS automatically, and every real domain config (NSe/config/nse_from_oceanicu.yaml and its siblings) validates hydrography/boundaries.*/meteo/river_discharge against it.
