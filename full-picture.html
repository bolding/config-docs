The full picture

The other docs each answer one focused question (PLAN.md: why does this data model look the way it does; docs/yaml_vs_python.md: what goes in a config file vs. a driver script; docs/providers.md: how does a project plug in its own data-provenance vocabulary). This doc is the missing zoomed-out view tying them together: what actually happens, in order, from "pyGETM is installed" to "a simulation is running from a validated config" — written after everything below existed, not as a plan for what would exist.

The pipeline, end to end

 ┌─────────────────┐
 │  live pygetm     │   introspects Domain, Simulation, boundary/river
 │  installation    │   collections, output requests, pluggable strategy
 └────────┬─────────┘   objects (vertical_coordinates, airsea, ...)
          │
          │ schema.build_schema()            <- ONLY function needing pygetm
          ▼
 ┌──────────────────────────┐
 │   PygetmConfigSchema      │  sections + enums + schema_fingerprint +
 │   (in-memory, or JSON     │  pygetm_version/pygetm_git_commit + warnings
 │   via `pygetm-config dump`)│
 └──┬───────────────────┬───┘
    │                   │
    │ yaml_template.py  │ session.py + frontends/textual_app.py
    │ write_template()  │ (edits a validated config against the schema;
    │                   │  needs the tui extra, NOT pygetm -- can run from
    │                   │  a JSON snapshot in a completely separate env)
    ▼                   ▼
 tiered YAML       interactively-edited
 template               config.yaml
    │                   │
    └─────────┬─────────┘
              ▼
     yaml_parse.validate_config()   <- needs the schema object, not pygetm itself
              │
              ▼
      validated config dict
              │
              ▼
      pygetm_config.loader          <- needs pygetm again, to actually build things
   build_domain -> add_open_boundaries -> add_rivers -> build_simulation ->
   apply_data_assignments -> configure_output -> start_simulation -> run_loop
   -> finish_simulation
              │
              ▼
      a running pyGETM simulation

pygetm-config run config.yaml --stop ... (or scripts/run_model.py) drives the whole right-hand path (validate -> loader) in one command. pygetm-config edit only ever touches the left/middle path (template -> TUI -> config.yaml) and can run in an environment that has never seen pygetm at all.

pygetm_config.codegen (pygetm-config run config.yaml --dump-python [PATH]) is a side branch off the validated-config box above: instead of feeding it to loader.py for real execution, it renders the SAME resolved values as a literal, standalone Python script (no pygetm_config import needed to run it) — real breakpoints, real prints, no config-driven abstraction between you and the actual pygetm.simulation.Simulation(...) call that's failing. It reuses loader.py's own value-resolution logic (_coerce_value, _resolve_choice, the strategy-slot registries) rather than re-deriving "what does this config resolve to" a second time, so there's still only one place that logic lives. Deliberately a one-off debugging aid, not a second source of truth: regenerate from the config next time rather than hand-maintaining the output.

Why two environments, concretely

Only schema.build_schema() imports pygetm (directly or transitively) — every other module (model, session, serialize, yaml_template, yaml_parse, both frontends, providers) works from an already-built PygetmConfigSchema object with zero pygetm dependency. This is enforced, not just an aspiration: .venv-tui is a throwaway dev venv with pygetm deliberately absent, used to develop and test the frontend so an accidental import pygetm fails loudly during development rather than only being noticed later. In practice this means: regenerate dist/schema.json once from a pygetm-capable environment (pygetm-config dump), then edit configs against that snapshot anywhere else — a laptop with no pygetm build toolchain at all, for instance.

Why a version-qualified schema snapshot, not just one schema.json

Two different pyGETM builds can expose an identical configurable surface — most commits are bug fixes or internal refactors that don't touch any constructor signature or docstring the introspection engine reads. schema_fingerprint is a content hash of sections+enums only (excluding pygetm_version/pygetm_git_commit/warnings, see serialize.compute_fingerprint), so it's the real "is this config still valid against the schema I have now" signal — a version or commit string alone would say "different" far more often than the configurable surface actually changed. scripts/dump_schema.py writes to dist/<version>[+<commit>]/schema.json and a dist/schema.json "latest" copy, so snapshots from different pyGETM builds are kept side by side rather than overwritten. pygetm_git_commit is best-effort (walks up from the installed package's __file__ looking for a .git directory) and is empty for a normal, non-editable install — not fabricated when unavailable.

Every ChoiceSpec keeps every alternative present, always

Originally built only for pygetm_config.providers (a config needed to keep meteo.ERA5: and meteo.CMIP6: both present so a different run-folder could switch source: without deleting/retyping a block), but generalized to EVERY ChoiceSpec in the schema after the same question came up for the core schema too: why should simulation.vertical_coordinates behave any differently? So vertical_coordinates, radiation, domain, the output.files per-file type choice — all of them — keep every alternative's fields present at once, each under its own <label>: sub-key, with only the top-level type:/source: field picking which is active:

simulation:
  vertical_coordinates:
    type: GVC
    Sigma: {ddu: 0.0, ddl: 0.0, ...}
    GVC: {nz: 40, ddu: 0.75, ddl: 0.75, Dgamma: 10.0, gamma_surf: true}
    Adaptive: {nz: 40, ...many more...}

Switching type: GVC to type: Adaptive needs no other edit — Adaptive:'s own values are already there. This makes a generated template genuinely a complete "global" reference document (every strategy's every param, for every slot, always present) rather than one path picked with the rest commented out as a note. Frontends (session.py/frontends/textual_app.py) only ever render the currently-active choice's fields, so this costs nothing in screen space despite the file always carrying everything.

yaml_parse.validate_config reads whichever <label>: sub-key matches the active discriminator, validates only that one, and preserves every other sub-key's block verbatim (unvalidated — it may reference a different, unrelated shape) in the output. It falls back to the old flat form (type: GVC, nz: 40, ... with no nested GVC: sub-key at all) for backward compatibility with configs written before this convention existed — nothing already written breaks. loader.py needed zero changes for any of this: it only ever consumes validate_config's already-flattened output, never the raw YAML shape.

A tour of one real config: nse_from_oceanicu.yaml

This file (and its driver, oceanicu_driver.py) live in the OceanICU repo, not here — OceanICU/oceanicu_3d/NSe/config/nse_from_oceanicu.yaml — since they're genuinely OceanICU-specific, unlike everything else this doc covers. Every section below actually exists in the current schema (build_schema() against live pygetm 0.9.28, verified while writing this doc) and is used, in this order, by that file:

Section key Node kind What it is
domain ChoiceSpec Build a Domain — create_cartesian/create_spherical/create_spherical_at_resolution/Domain itself (the general path), or BathymetryFile (method: BathymetryFile), a pygetm-config convenience for the common "read a pre-prepared bathymetry NetCDF" case (path + variable names + mask convention) — unified into one ChoiceSpec (previously two separate sections, domain:/bathymetry:; see loader.build_domain). This is what nse_from_oceanicu.yaml actually uses.
open_boundaries CollectionSpec Boundary positions + condition types, one entry per add_by_index call — nse_from_oceanicu.yaml's 9 entries, converted verbatim from OceanICU's cfg_boundaries.py.
rivers CollectionSpec River positions added by name/location — distinct from river_discharge, a provider-registry role for where the discharge data itself comes from (see docs/providers.md). Empty in this example; positions come dynamically from oceanicu_driver.py's add_rivers.
simulation + 6 sub-sections ObjectSpec/ChoiceSpec runtype/Dcrit/Dmin plus pluggable strategy slots (vertical_coordinates, internal_pressure, airsea, vertical_mixing, radiation) and two plain object sections (momentum, density).
runtime ObjectSpec timestep/split_factor/time (start) plus the switches.* booleans (dump_on_error, profile, check_finite) — deliberately excludes stop, since start/stop are per-invocation (--start/--stop), not part of a reusable setup.
data_assignments CollectionSpec "Set this field to this constant/file" entries — not used in this example (the physics fields here are all left at their strategy-object defaults).
output + output.files + output.variable_request ObjectSpec/CollectionSpec output.folder (shared directory prefix) plus one entry per output file with its variable list inlined.

This file also has real, schema-validated hydrography:/boundaries: {barotropic, baroclinic}/meteo:/river_discharge: sections — provider roles registered by OceanICU/oceanicu_3d/driver/oceanicu_providers.py (discovered via PYGETM_CONFIG_PROVIDERS, which oceanicu_driver.py sets automatically) — see docs/providers.md for the full contract and the nested-by-label convention these (and every other ChoiceSpec) now use.

The lifecycle for a brand-new project (not just OceanICU)

  1. Get a schema snapshot. In any pygetm-capable environment: pygetm-config dump -o schema.json (or just call build_schema() directly in Python if you're staying in that environment).
  2. Generate a starting template. pygetm-config template -o config.yaml --tier basic gives a config with every BASIC-tier field present (commented guidance for ADVANCED/EXPERT fields, per --tier/--hide-expert).
  3. Fill it in, either by hand or via pygetm-config edit --schema schema.json config.yaml (the Textual TUI — works with zero pygetm installed, see above).
  4. Decide what's genuinely bespoke. Most setups need nothing beyond the YAML — docs/yaml_vs_python.md walks through exactly which real OceanICU code turned out to be pure data (boundary positions, even the previously-thought-bespoke bathymetry-file reading, now domain:'s own BathymetryFile choice) vs. genuinely needing a driver script (OceanICU's dynamic, threshold-filtered river loading). If your setup needs the latter, write a small driver script that calls loader.build_domain/add_rivers/etc. individually instead of run_from_config — see OceanICU/oceanicu_3d/driver/oceanicu_driver.py (a separate repo) for the pattern: every loader.py function takes an already-built domain/sim as an argument rather than constructing it internally, so a bespoke first step doesn't force you to reimplement everything downstream of it too.
  5. If you need your own data-provenance vocabulary (where does forcing data actually live, per source) rather than OceanICU's, register a pygetm_config.providers entry point — see docs/providers.md for the full contract and two real worked examples (OceanICU's, and a second, unrelated hypothetical project's, proving the mechanism itself carries no OceanICU assumptions).
  6. Validate and run. pygetm-config validate config.yaml to check without running anything; pygetm-config run config.yaml --stop ... to actually run it, with --print-config/--list-output/--plot-domain/--dry-run available for debugging before committing to a full run (see README.md's flag list, mirroring the spirit of OceanICU's own run_model.py CLI overrides but with a project-agnostic generic --set KEY=VALUE instead of per-project flags).

What's still explicitly out of scope

  • pre_transform_expression (an arbitrary-string unit-conversion escape hatch the schema documents as schema-only intent): the loader raises LoaderError rather than evaluating it — running an arbitrary string sourced from a YAML config file is a real code-execution risk even with a restricted eval(). Not a gap to be closed casually; would need a real sandboxing story first.
  • DataSourceSpec.role="domain_grid_field": Domain's raw array-typed constructor parameters (H, mask, lon, lat, ...) have no InputManager available yet at construction time in pyGETM itself, so this is schema-only intent for a future loader capability, not something that runs today (domain:'s own BathymetryFile choice covers the common sub-case of this directly, via its own bespoke NetCDF-reading code in loader.py, without needing this general pathway).
  • Auto-deriving data_assignments: entries from a provider choice: providers.py gets you a validated "where does this data live" answer (source: ERA5, folder: ...); turning THAT into the concrete per-field data_assignments: entries (file path + variable name + any unit conversion, one per required field) is not automated -- you write them by hand, once per setup, same as nse_from_oceanicu.yaml now does for its meteo forcing. The underlying mechanism those entries use (kind: file + pre_transform_scale/pre_transform_offset, resolving to a real pygetm.input.from_nc(...) call) already works today, verified against real ERA5 files -- see docs/yaml_vs_python.md.
  • pygetm-config stays independent of ocean-stack. OceanICU's own driver/oceanicu_driver.py does import pygetm_config directly and depends on it being importable in its environment, but pygetm-config is still deliberately not wired into ocean-stack's own environment.yml or any other repo's dependency list -- see PLAN.md's "Repo placement" section for why.
