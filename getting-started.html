Getting started

The other docs assume you already know why this tool exists and roughly what it looks like. This one doesn't — it's for someone who has pyGETM installed, has never touched pygetm-config before, and wants to go from nothing to a real, running simulation, one small step at a time. Every example below was actually run, not just written — copy-paste any of it and it works as-is, no external data files needed until the very last section.

Two layers of knowledge, not one

Before diving in, it's worth being explicit about something that isn't obvious from the README: building a complex setup with pygetm-config draws on two genuinely different kinds of knowledge, and this tool only replaces one of them.

  1. pyGETM's own configuration surface — what a Domain takes, what Simulation takes, what an open boundary or an output file takes. This is what the YAML file and its schema are for. You don't need to know pyGETM's Python API to use it — the schema is introspected live from a real pyGETM install, so every field you can set in the YAML is a real constructor/method parameter, with the same name, same type, same default.
  2. Project-specific domain knowledge and Python — which hydrography source to use, how open boundary segments correspond to a real coastline, and genuinely dynamic logic that isn't expressible as static data at all (OceanICU's river loading is the running example: which rivers to include is threshold-filtered from a NetCDF file at run time, not a fixed list — no YAML shape captures "compute this list right before using it"). pygetm-config's answer to this second layer is the script hook convention (data_script/script/post_data_script fields pointing at path/to/file.py:function_name) — see OceanICU's own scripts/rivers.py, scripts/hydrography.py, scripts/meteo.py for real, worked examples, and docs/yaml_vs_python.md for how to tell which category a given piece of config falls into.

Layer 1 is what this tutorial teaches. Layer 2 is inherently project-specific — the closest thing to a tutorial for it is reading OceanICU's real scripts and nse_from_oceanicu.yaml once you're comfortable with the basics below.

Setup

Two environments matter, and you'll only need the first one for this tutorial:

  • A pygetm-capable environment (conda activate pygetm or similar) — needed for anything that actually builds a domain/simulation: pygetm-config run, validate, dump, template, and nest for a nested setup of several models (needs the pyGETM fork with nesting; docs/nesting.md).
  • A pygetm-free environment (.venv-tui) — only needed for the Textual TUI (pygetm-config edit), which works from a schema snapshot (dist/schema.json) without pyGETM installed at all. Not used below, but worth knowing it exists once your config gets bigger than you want to hand-edit.

Step 1: the smallest config that runs

A domain, nothing else. create_cartesian (flat, meter-based coordinates, not real geography) keeps this self-contained — no bathymetry file needed. airsea.type: Fluxes matters here: the default airsea handler (FluxesFromMeteo) requires real meteo data to be set before it'll run, and we don't have any yet. Plain Fluxes doesn't.

# step1.yaml
domain:
  method: create_cartesian
  x: [0.0, 1000.0, 2000.0, 3000.0, 4000.0]
  y: [0.0, 1000.0, 2000.0, 3000.0, 4000.0]
  H: 10.0
  f: 1.0e-4

simulation:
  runtype: BAROTROPIC_2D
  airsea:
    type: Fluxes

runtime:
  time: "2024-01-01T00:00:00"
  timestep: 10.0
  split_factor: 1

$ pygetm-config validate step1.yaml
valid
$ pygetm-config run step1.yaml --dry-run
...
dry run: built and started successfully, time=2024-01-01 00:00:00

--dry-run builds and starts the simulation but never advances it — the fastest way to check a config is actually constructible before committing to a real run. validate is faster still (no domain/simulation build at all, just schema checking) — reach for it first when iterating on a large config.

Variant: coordinates from linspace/arange, depth from a file

Spelling out x/y (or lon/lat for create_spherical) as a literal list gets unwieldy past a handful of points. Any array_like field (x, y, lon, lat, H, f, mask, z0, ...) also accepts a small dict instead of a literal value or list — kind: linspace/kind: arange mirror numpy.linspace/numpy.arange's own arguments exactly; kind: file reads a variable from a real NetCDF file:

domain:
  method: create_cartesian
  x: {kind: linspace, start: 0.0, stop: 4000.0, num: 5}
  y: {kind: linspace, start: 0.0, stop: 4000.0, num: 5}
  H: {kind: file, file: bowl_bathy.nc, variable: H}
  f: 1.0e-4

H's file needs to be built at the same resolution as the domain's own cell centers — pygetm maps a file-provided array onto the grid purely by shape ((ny, nx) at cell centers, (ny+1, nx+1) at cell corners, or a scalar to broadcast), there's no coordinate-based interpolation in this path. For anything genuinely lower/higher resolution than the domain (a real GEBCO tile, say), reach for domain: {method: BathymetryFile, ...} instead (see docs/overview.md), which does real regridding.

A small, real, standalone script to build a matching bowl-shaped bowl_bathy.nc — 5 m deep at the center, 20 m at the edges, on the exact same 5×5 x/y grid as above:

import numpy as np
import netCDF4

nx, ny = 5, 5
x = np.linspace(0.0, 4000.0, nx)
y = np.linspace(0.0, 4000.0, ny)
X, Y = np.meshgrid(x, y)
cx, cy = x.mean(), y.mean()
r = np.sqrt((X - cx) ** 2 + (Y - cy) ** 2)
H = 5.0 + 15.0 * (r / r.max())  # shallow bowl center, deeper at the edges

with netCDF4.Dataset("bowl_bathy.nc", "w") as nc:
    nc.createDimension("x", nx)
    nc.createDimension("y", ny)
    nc.createVariable("x", "f8", ("x",))[:] = x
    nc.createVariable("y", "f8", ("y",))[:] = y
    nc.createVariable("H", "f8", ("y", "x"))[:] = H

Genuinely tested, both directions: this exact x/y/H combination builds and starts a real simulation (pygetm-config run ... --dry-run, volume reflects the varying depth, not a flat one), and the same linspace/kind: file pattern works identically for create_spherical's lon/lat (tested with a small lon/lat bowl file the same way). Use this as a starting point for your own depth field — replace the bowl formula with whatever real bathymetry you have, keeping the file's grid resolution matched to x/y (or lon/lat).

Step 2: a real open boundary, and an actual run

Adding an open boundary needs two things: the boundary's position (open_boundaries:, a list — one entry per contiguous segment) and its value (data_assignments:, described below). type_2d: FLATHER_ELEV is a real pyGETM boundary condition type (radiating elevation).

# step2.yaml
domain:
  method: create_cartesian
  x: [0.0, 1000.0, 2000.0, 3000.0, 4000.0]
  y: [0.0, 1000.0, 2000.0, 3000.0, 4000.0]
  H: 10.0
  f: 1.0e-4

open_boundaries:
  - side: WEST
    l: 0
    mstart: 0
    mstop: 5
    type_2d: FLATHER_ELEV

simulation:
  runtype: BAROTROPIC_2D
  airsea:
    type: Fluxes

runtime:
  time: "2024-01-01T00:00:00"
  timestep: 10.0
  split_factor: 1

data_assignments:
  - target: open_boundaries.z
    kind: constant
    constant_value: 0.1

data_assignments is the generic "where does this value come from" list — every entry has a target (a dotted path into the live simulation) and a kind (constant, file, tpxo, or boundary_type — see docs/overview.md for the full picture). open_boundaries.z (plural open_boundaries, not open_boundary) is deliberate: barotropic elevation/transport fields live directly on sim.open_boundaries, not per-tracer — this is one of the places pygetm-config's own docstrings exist specifically because the naming isn't obvious from pyGETM's API alone.

Now a real run, not just --dry-run:

$ pygetm-config run step2.yaml --stop 2024-01-01T00:05:00
...
INFO:pygetm_config.loader:open_boundaries.z.set(0.1)
...
INFO:root:2024-01-01 00:05:00
finished: time=2024-01-01 00:05:00

Five real minutes of simulated time, forced by a constant 0.1 m boundary elevation. Every .set()/constructor call pygetm-config makes on your behalf is logged at INFO level — if you're ever unsure what a config value actually does, run it and read the log.

Step 3: output

# step3.yaml -- everything from step2.yaml, plus:
output:
  files:
    - type: netcdf
      path: tutorial_out.nc
      interval: 1
      interval_units: MINUTES
      variable_requests:
        - fields: [zt, u1, v1]

$ pygetm-config run step3.yaml --stop 2024-01-01T00:05:00
...
INFO:pygetm_config.loader:sim.output_manager.add_netcdf_file(path=PosixPath('tutorial_out.nc'), interval=1, interval_units=<TimeUnit.MINUTES: 3>)
INFO:pygetm_config.loader:output.files[0].request('zt', 'u1', 'v1')
...
finished: time=2024-01-01 00:05:00
$ ls -la tutorial_out.nc
-rw-rw-r-- 1 kb kb 50433 ... tutorial_out.nc

output.files is a plain list — as many files as you want, each with its own real add_netcdf_file/add_zarr_file/etc. parameters (interval, compression, whatever the real pyGETM method accepts) and its own field list. output.variable_groups (not shown here) lets you name a reusable set of fields instead of repeating a long list across files — see nse_from_oceanicu.yaml for a real example once you have more than a handful of output variables.

Step 4: seeing the real pyGETM code

$ pygetm-config run step3.yaml --stop 2024-01-01T00:05:00 --dump-python generated.py
wrote generated.py

This writes a standalone script — no pygetm_config import needed to run it, just literal, ordinary pyGETM calls. Worth actually reading once: it's the most direct way to build a mental model of what your YAML means in terms of the real API, and it doubles as a debugging aid (real breakpoints, real prints, nothing hidden behind an abstraction layer).

It's also worth treating as a genuine archival artifact, not just a debugging convenience. --dump-python also writes a companion ..._config.yaml — the fully validated, merged config as it actually was at generation time, ${VAR} references and all. Together, the generated script + its config snapshot are a single, self-contained, frozen record of exactly what a given run actually did: no dependency on the live pygetm-config schema version, no dependency on nse_from_oceanicu.yaml having stayed unchanged since — both of which keep evolving. Six months from now, "what was my exact setup for this specific run" is answered by that one generated file, not by trying to reconstruct it from a config that's since been edited and a driver whose schema has moved on. Worth keeping the generated script + config pair alongside a run's actual output, not regenerating on demand and discarding.

One thing worth being explicit about: the generated script's shape — create_domain() / create_simulation(domain) / configure_output(sim) / run(sim) / main() — mirrors OceanICU's own run_model.py conventions. That's a deliberate choice for continuity within OceanICU (so a generated script reads like the hand-written scripts this project already had), not a pyGETM requirement. A pyGETM run is fundamentally just: build a domain, build a simulation, .set() some values, sim.start(), loop sim.advance(). There's nothing about pygetm-config or pyGETM that requires that specific function-per-phase structure — if you're starting a project with no existing script conventions to match, feel free to write your own driver shaped however makes sense to you; pygetm_config.loader's individual functions (build_domain, add_open_boundaries, build_simulation, apply_data_assignments, configure_output, start_simulation, ...) are meant to be called piece by piece from whatever structure you actually want, not just from run_from_config's own all-in-one convenience wrapper.

Concretely — written by hand, not generated, using pygetm_config's own loader API directly: a deliberately non-OceanICU-shaped driver for step3.yaml above, no functions at all, just linear top-to-bottom code:

import datetime

from pygetm_config.loader import (
    build_domain, add_open_boundaries, check_domain_cfl, build_simulation,
    apply_data_assignments, configure_output, start_simulation, run_loop,
    finish_simulation,
)
from pygetm_config.schema import build_schema
from pygetm_config.yaml_parse import validate_config
import yaml

with open("step3.yaml") as f:
    raw = yaml.safe_load(f)

schema = build_schema()
config, errors = validate_config(raw, schema)
assert not errors, errors

domain = build_domain(config, schema)
add_open_boundaries(domain, config, schema)
check_domain_cfl(domain)

sim = build_simulation(domain, config, schema)
apply_data_assignments(sim, domain, config, schema)
configure_output(sim, config, schema)
start_simulation(sim, config, schema)

run_loop(sim, config, datetime.datetime.fromisoformat("2024-01-01T00:05:00"))
finish_simulation(sim)

Genuinely run, not just written — same real simulation as pygetm-config run step3.yaml --stop 2024-01-01T00:05:00, just without any pygetm_config CLI, --dump-python, or OceanICU-style function boundaries involved at all. Every loader.* function takes an already-built domain/sim/config rather than constructing anything internally, specifically so a script like this — or a Jupyter notebook, or a class-based structure, or whatever else fits your own project — can call exactly the pieces it needs, in whatever order and shape make sense, and skip the rest (no open_boundaries: at all? skip add_open_boundaries entirely).

--dump-python can produce this same shape too — a flat, --dump-python-style flat script is the literalized/frozen equivalent of the linear driver above (same statement order, same variable names, real values baked in, no pygetm_config import needed to run it) instead of the default create_domain()/create_simulation(domain)/configure_output(sim)/ run(sim)/main() structure:

$ pygetm-config run step3.yaml --stop 2024-01-01T00:05:00 --dump-python generated_flat.py --dump-python-style flat
wrote generated_flat.py

Useful as a starting point in its own right: a flat, frozen script is easier to manually cut into and extend line by line than one already split across four functions — e.g. if you're about to hand-add something project-specific this config format doesn't know about, and you don't yet know exactly where in the pyGETM call sequence it needs to go.

generated_flat.py starts with the exact same header every --dump-python output has (imports, embedded helpers, a real argparse parser — style only changes what comes after args = parser.parse_args()). The excerpt below picks up right there:

# ... imports, resolve_data_path/apply_data_roots, argparse, args = parser.parse_args()
# (identical to the "functions" style above) omitted here -- this is an excerpt,
# not the full file; run the command above to get something you can execute as is.

# --- domain ---
domain = pygetm.domain.create_cartesian(
    x=np.array([0.0, 1000.0, 2000.0, 3000.0, 4000.0], dtype=float),
    y=np.array([0.0, 1000.0, 2000.0, 3000.0, 4000.0], dtype=float),
    H=10.0,
    f=0.0001,
)

# --- open_boundaries ---
domain.open_boundaries.add_by_index(
    side=pygetm.open_boundaries.Side.WEST,
    l=0,
    mstart=0,
    mstop=5,
    type_2d=4,  # FLATHER_ELEV
    type_3d=1,  # ZERO_GRADIENT
)

print(f"domain.cfl_check() -> max stable 2D timestep {domain.cfl_check():.3f} s")

# --- simulation ---
airsea = pygetm.airsea.Fluxes(
)
sim = pygetm.simulation.Simulation(
    domain,
    runtype=pygetm.constants.RunType.BAROTROPIC_2D,
    airsea=airsea,
)

# --- data_assignments ---
sim.open_boundaries.z.set(0.1)

# --- output ---
output_file_0 = sim.output_manager.add_netcdf_file(
    path=pathlib.Path(resolve_data_path('tutorial_out.nc')),
    interval=1,
    interval_units=pygetm.output.TimeUnit.MINUTES,
)
_request_output_fields(output_file_0, ['zt', 'u1', 'v1'], skip_unavailable=args.skip_unavailable_output, label='output.files[0].variable_requests[0]')

if args.save_restart:
    sim.output_manager.add_restart(args.save_restart)

# --- start ---
_start_kwargs = dict(
    timestep=10.0,
    split_factor=1,
)
if args.load_restart:
    _start_kwargs['time'] = sim.load_restart(args.load_restart)
elif args.start:
    _start_kwargs['time'] = datetime.datetime.fromisoformat(args.start)
else:
    print('runtime.time is required (or pass --start / --load-restart)', file=sys.stderr)
    sys.exit(1)
sim.start(**_start_kwargs)

if not args.dry_run and args.stop:
    stop = datetime.datetime.fromisoformat(args.stop)
    while sim.time < stop:
        sim.advance(check_finite=False)
elif args.dry_run:
    print(f"dry run: built and started only, not advanced, time={sim.time}", file=sys.stderr)
else:
    print("no --stop given -- not advancing", file=sys.stderr)
sim.finish()

Genuinely the real output of the command above, for step3.yaml — not hand-transcribed. Compare it against the linear driver higher up: same shape, but this one is what pygetm-config itself would produce from any config, including one far too large to comfortably hand-write a driver for.

pyGETM's own real example set (a separate repo) is the other direction entirely: hand-written scripts and notebooks (north_sea.py, box_spherical.py, open_boundaries.ipynb, test_vertical_coordinates.ipynb, and many more), each built directly against pyGETM's raw API with no config-file layer at all — plain argparse and literal constructor calls, no schema, no generation step. Worth browsing if you want to see the breadth of what pyGETM itself can do (GOTM coupling, FABM, different domain shapes, parallel runs) independent of pygetm-config, or if you're trying to understand a pyGETM feature that isn't yet exercised by anything OceanICU-specific — they're the canonical "write the Python by hand" reference, the mirror image of the YAML-first/generate-the-Python approach this tool takes.

Step 5: when you need real Python

Everything so far was expressible as static YAML because every value was either fixed at config-write time or a plain file read. Real setups eventually hit something that genuinely can't be — OceanICU's rivers are the concrete example: which rivers to include, and their actual discharge values, are computed from a real NetCDF file (threshold-filtered) at run time, not knowable when you write the YAML.

pygetm-config's answer is the script hook: a config field pointing at path/to/file.py:function_name, loaded and called with the live domain/sim object already built. river_discharge.emorid.script / .data_script in nse_from_oceanicu.yaml, pointing at real functions in scripts/rivers.py, is the worked example — read that file's own docstring for the exact contract (what arguments it receives, what it's expected to do). The same convention covers hydrography initial conditions (scripts/hydrography.py) and meteo-source-specific data wiring (scripts/meteo.py).

The rule of thumb for "does this need a script hook, or is it just data": if you can write down the value (or the file it comes from) today, independent of anything the simulation computes at run time, it's data_assignments. If it depends on real-time information (today's actual river list above a threshold, a value derived from another live config field) or needs a real Python loop/conditional to construct, it's a script hook. docs/yaml_vs_python.md walks through OceanICU's own conversion in detail — several things that looked bespoke (bathymetry-file reading, in particular) turned out to be pure data once actually checked against the reference code, so it's worth verifying rather than assuming.
