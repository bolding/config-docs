pygetm-config

An introspection-driven configuration schema for pyGETM.

pyGETM has no native YAML/config file format of its own — a model setup is built by calling its well-typed, well-documented Python constructors and methods directly. pygetm-config introspects pyGETM's live Python API (Domain, Simulation, boundary/river collections, output requests, pluggable strategy objects like vertical_coordinates/internal_pressure/ airsea, ...) to build a structured, general-purpose model of "everything configurable in a pyGETM setup", tiered by importance (basic / advanced / expert), plus round-trip YAML support (template generation with inline help text, and parsing/validation).

This package is independent of any particular project (OceanICU or otherwise) and independent of the ocean-stack umbrella environment. It has no dependency on either beyond pygetm itself (only required for the introspection engine — the data model and YAML round-trip code work from a pre-generated schema snapshot with no pygetm import needed).

See docs/overview.md for the full zoomed-out picture (the whole pipeline from introspection to a running simulation, a section-by-section tour of a real converted config, and the end-to-end lifecycle for a brand-new project) if you're looking for how everything below fits together, not just the individual pieces.

Nested setups

pygetm-config nest master.yaml --out RUN builds a nested setup for the two-way nesting of the pyGETM fork (bolding/pygetm, branch nesting-mpmd): from one master file (a base configuration, the levels' layout, per-level overrides) every level's configuration and run script, and a launch script (mpiexec, optionally a Slurm job). Opt-in: single-model configurations are unaffected. See docs/nesting.md.

Scope

This package builds and validates the schema, includes a Textual TUI frontend for editing configs against it, and (pygetm_config/loader.py) can build a live pyGETM Domain/Simulation from a validated config and actually run it. See PLAN.md for the full design.

To run a model from a config:

conda activate pygetm  # the loader needs pygetm, same as introspection
pygetm-config run config.yaml --stop 2020-06-01
# or: python scripts/run_model.py config.yaml --stop 2020-06-01

--dry-run builds and starts the simulation without advancing it (useful to check a config actually constructs successfully). loader.py's target-path grammar for data_assignments (domain.<attr>, simulation.<attr...>, river.<name>.<attr>, open_boundary.<variable>.<attr> per-tracer, open_boundaries.<field> plural for the barotropic z/u/v fields -- e.g. kind: tpxo) and its array_like/pre_transform handling are documented in the module's own docstring, including the known gaps (e.g. pre_transform_expression is rejected outright rather than evaluated, since running an arbitrary string from a config file is a real code-execution risk).

pygetm-config run also has a set of debugging flags in the spirit of OceanICU's own run_model.py CLI overrides (verified against that script): --print-config, --list-output, --plot-domain [path], --no-boundaries/--no-rivers/--no-output, --output-dir, --runtype, --profile [name], --load-restart/--save-restart, --skip-unavailable-output, --log-level (real user need: the config-driven abstraction makes it hard to see what actual pyGETM calls are happening underneath -- loader.py logs every one, with real resolved arguments, at INFO by default; --log-level DEBUG also shows one line per open_boundaries/rivers entry, not just a summary count — see loader.py's module docstring "Debugging" note), --dump-python [PATH] (real user need: sometimes even the logged native calls aren't enough, and you want to actually set a breakpoint or add a print inside the real construction sequence — this writes a self-contained, standalone script implementing the config as literal pygetm/pygetm.domain/pygetm.simulation calls, no pygetm_config import needed to run it, then exits without running anything here; see pygetm_config/codegen.py's module docstring for the "regenerate when the config changes, don't hand-maintain" scoping. The script is structured into real functions — create_domain(), create_simulation(domain), configure_output(sim), run(sim), and a real main() that calls all four in order under if __name__ == '__main__': — mirroring OceanICU's own run_model.py exactly (including its own main()/__main__ shape), not one long flat sequence of statements. The full validated config is written to a companion <name>_config.yaml file alongside the script (read back via Path(__file__).parent, so the pair stays runnable together regardless of the current working directory) instead of being embedded as one giant inline literal. The generated script has its own real argparse CLI — --start/--stop/--dry-run/--load-restart/--save-restart/--skip-unavailable-output are genuine runtime arguments of that script, defaulting to whatever was given to --dump-python, not fixed at generation time; the same generated file is rerunnable with different ones without regenerating. Any file/folder config field can reference ${VAR}/$VAR (standard POSIX env-var syntax) instead of a hardcoded machine-specific path — kept literal all the way through validation and generation, resolved only at the point of actual file access (in both real execution and the generated script — see loader.resolve_data_path), so a config or a generated script + companion YAML stays copyable across machines; each machine supplies its own values via real env vars, --data-root NAME=VALUE (repeatable, on both pygetm-config run and every generated script's own CLI, always wins), or an optional --data-roots-file (a flat YAML file, no hostname-keying — only fills gaps not already exported, never overrides a real env var or --data-root; see loader.apply_data_roots). Genuinely bespoke steps (a real, project-specific need, e.g. rivers read from a live external file, not expressible as static YAML) can be included too via a "path/to/file.py:function_name" config field (same convention as PYGETM_CONFIG_PROVIDERS), at three distinct points in the pipeline: <role>.script (before the simulation object exists, e.g. river_discharge.script — func(domain, config), real POSITIONING), <role>.data_script (after data_assignments, e.g. river_discharge.data_script — func(sim, domain, config), real DATA — a second, distinct function on the same role, since e.g. river position and river discharge data are two separate steps mirroring OceanICU's own cfg_rivers.py's real create()/data() split), and post_data_script (also after data_assignments, for anything that isn't role-specific, e.g. a substitution that reads an already-assigned field — func(sim, domain, config); see loader.run_post_data_script's own docstring for why this can't just run right after sim exists). See loader.run_river_discharge_script/codegen._emit_river_discharge_script, loader.run_river_discharge_data_script/codegen._emit_river_discharge_data_script, and loader.run_post_data_script/codegen._emit_post_data_script; the referenced function's real source is embedded, never an eval'd/exec'd string from the YAML), and a generic --set KEY=VALUE (repeatable) for ad hoc overrides of anything in the config — see pygetm-config run --help. Not every project-specific override oceanicu has (e.g. --tpxo_dir) is a dedicated flag here; --set covers that generically instead, since this tool is project-agnostic. See docs/yaml_vs_python.md for why that split exists, and OceanICU/oceanicu_3d (a separate repo — NSe/config/nse_from_oceanicu.yaml + driver/oceanicu_driver.py) for a worked conversion of a real OceanICU config; this repo's own examples/ only has project-agnostic material (see docs/providers.md for why).

Two environments: introspection vs. frontend

Only pygetm_config.schema.build_schema() requires pygetm to be importable — nothing else in this package does, including either frontend (pygetm_config.session, pygetm_config.frontends.textual_app, pygetm_config.frontends.web_app). The intended split:

  • A pygetm-capable env (e.g. a conda env with pygetm installed): used only to regenerate a schema snapshot, pip install -e ".[introspect,dev]" then pygetm-config dump -o schema.json.
  • Anywhere else, with no pygetm at all: pip install -e ".[tui,dev]" then pygetm-config edit --schema schema.json config.yaml for the Textual frontend, or pip install -e ".[web,dev]" then pygetm-config web --schema schema.json config.yaml for the FastAPI web frontend (open the printed http://127.0.0.1:8000 URL) — both run against the same schema snapshot, pick whichever fits your terminal-vs-browser preference. tui and web have zero import overlap with each other either, so installing one never drags in the other's dependency.

This is enforced, not just documented — see .venv-tui in development (a throwaway, gitignored venv with pygetm deliberately absent, used to develop/test both frontends so an accidental pygetm import fails loudly).

Development

# introspection side (needs a pygetm-capable env)
conda activate pygetm
pip install -e ".[introspect,dev]"
pytest
python scripts/dump_schema.py   # writes dist/schema.json + template YAMLs

# frontend side (must NOT have pygetm installed)
python3 -m venv .venv-tui
.venv-tui/bin/pip install -e ".[tui,dev]"
.venv-tui/bin/pytest

Tests that require a live pygetm import are marked requires_pygetm/guarded by pytest.importorskip("pygetm") and skip automatically if pygetm isn't importable (e.g. in .venv-tui). Tests that require textual (the Textual-driven Pilot tests) are guarded by pytest.importorskip("textual") and skip in the pygetm-only env. Running pytest in either env alone therefore only exercises what that env can actually support — run it in both to cover everything.
